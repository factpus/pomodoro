# アーキテクチャ

最終更新: 2026-08-20

## 状態同期

Vercel Functionsは常駐プロセスを保証しないため、Socket.IOサーバーとプロセスメモリを共有状態の正として使いません。各クライアントは1秒間隔でAPIから状態を同期し、5秒間隔で参加状態を更新します。

Redisに保存するタイマー状態には `phaseEndsAt`、`pausedRemainingSeconds`、`version`、各時間設定、完了回数を含めます。稼働中の残り時間はカウンターではなく `phaseEndsAt - serverNow` から算出するため、バックグラウンドタブや一時切断でドリフトしません。

## 整合性

更新処理はルーム単位のRedis分散ロック内で行います。ルームには24時間のTTL、参加者には15秒の生存期限があります。読み取り時にも経過済みフェーズをサーバー時刻で進めるため、常駐タイマー処理は不要です。

## 権限と入力

作成時に256-bitのホストトークンを発行し、ブラウザのsessionStorageへ保存します。サーバーにはSHA-256ハッシュだけを保存し、比較はタイミング攻撃に配慮して行います。招待URLにはトークンを含めません。

ルーム名、時間設定、クライアントID、操作コマンドはZodで検証します。作成・読み取り・生存確認・操作にはIP単位のレート制限があります。

## 障害時

共有ルームでは切断中にローカル状態へ分岐せず、操作を止めて「再接続中」と表示します。復帰時にRedisの状態を取得して自動復元します。Redisがない本番環境では、共有できるように見せかけず503を返します。

## 将来の拡張

同期方式はクライアントAPI層に分離しています。利用規模が大きくなり1秒ポーリングのコストが問題になった場合、状態モデルや権限モデルを保ったままSSE、WebSocket、マネージドRealtimeへ置き換えられます。
